# 6. Functional Requirements

Requirement IDs are stable identifiers referenced from API design, test plans, and tickets. Format: `FR-<MODULE>-<NNN>`.

## 6.1 Authentication (AUTH)

| ID | Requirement |
|---|---|
| FR-AUTH-001 | System shall authenticate users via email + password, issuing a short-lived JWT access token and a long-lived rotating refresh token. |
| FR-AUTH-002 | System shall enforce password complexity (min 10 chars, at least 1 upper, 1 lower, 1 number) at signup and reset. |
| FR-AUTH-003 | System shall hash passwords with bcrypt/argon2 (never reversible, never logged). |
| FR-AUTH-004 | System shall scope every authenticated request to exactly one `gym_id` (except Platform Super Admin), derived from the JWT, never from client-supplied input. |
| FR-AUTH-005 | System shall lock an account for a configurable cooldown after N consecutive failed login attempts. |
| FR-AUTH-006 | System shall support password reset via time-limited, single-use email token. |
| FR-AUTH-007 | System shall allow staff/member account activation only via an invite token generated by an authorized inviter (Owner → Trainer/Receptionist; Owner/Receptionist → Member). |
| FR-AUTH-008 | System shall allow a user to view and revoke their own active sessions. |
| FR-AUTH-009 | System shall log every authentication event (login success/failure, logout, token refresh, password reset) to the audit log. |

## 6.2 Gym Management (GYM)

| ID | Requirement |
|---|---|
| FR-GYM-001 | Gym Owner shall create and edit gym profile: name, logo, address, contact, timezone, currency, operating hours. |
| FR-GYM-002 | System shall enforce one active `gym` record per Gym Owner account at v1 (multi-gym ownership reserved for v2). |
| FR-GYM-003 | System shall support a `branch` entity linked to `gym`, defaulting to exactly one implicit branch per gym at v1 (UI hidden, schema present). |
| FR-GYM-004 | Gym Owner shall configure attendance rules (grace period, max session duration, self-check-in allowed y/n). |
| FR-GYM-005 | Gym Owner shall configure streak rules (which of check-in / workout-logged / check-out are required for a streak credit). |

## 6.3 User & Staff Management (USR)

| ID | Requirement |
|---|---|
| FR-USR-001 | Gym Owner shall invite a Trainer or Receptionist by email; invitee completes account setup via emailed link. |
| FR-USR-002 | Gym Owner shall deactivate a staff account, immediately revoking all active sessions for that account. |
| FR-USR-003 | Deactivating a Trainer shall not delete their historical assignments/notes; it shall block new assignments and require reassignment of active members. |
| FR-USR-004 | Platform Super Admin shall activate/suspend a gym tenant; suspension blocks all non-Owner login and shows the Owner a billing-status banner. |

## 6.4 Member Management (MEM)

| ID | Requirement |
|---|---|
| FR-MEM-001 | Receptionist or Owner shall register a new member with required fields (name, phone, email optional, DOB, gender, emergency contact) and optional health notes/photo. |
| FR-MEM-002 | System shall enforce phone-number uniqueness per gym (not globally — the same phone may belong to members at different gyms). |
| FR-MEM-003 | System shall derive member status automatically from membership state: `active`, `expired`, `frozen`, `inactive` (no active plan ever assigned), `cancelled`. |
| FR-MEM-004 | Owner/Receptionist shall assign or reassign a member's primary trainer. |
| FR-MEM-005 | System shall support member search by name/phone/email and filter by status, trainer, plan, join-date range. |
| FR-MEM-006 | Member self-service edit shall be limited to a defined field allowlist (contact info, photo, notification preferences); all other fields are staff-writable only. |

## 6.5 Membership Plans (PLAN)

| ID | Requirement |
|---|---|
| FR-PLAN-001 | Owner shall define membership plans with duration (days), price, description, and included features. |
| FR-PLAN-002 | System shall calculate membership expiry date as `start_date + plan.duration_days`, adjusted for any freeze days applied during the term. |
| FR-PLAN-003 | Staff shall renew a membership, creating a new membership period record linked to a payment. |
| FR-PLAN-004 | Staff shall upgrade/downgrade a member's plan; system shall pro-rate or flag manual adjustment per gym's configured policy. |
| FR-PLAN-005 | Staff shall freeze a membership for a date range with a reason; system shall extend expiry by the frozen duration and pause streak/attendance expectations for that range. |
| FR-PLAN-006 | System shall generate expiry notifications at configurable lead times (e.g., 7/3/1 days before expiry) and on the expiry day. |

## 6.6 Attendance & Check-in/Check-out (ATT)

| ID | Requirement |
|---|---|
| FR-ATT-001 | System shall record a check-in event with timestamp, method (manual/self/QR-future), and recorded-by user. |
| FR-ATT-002 | System shall record a check-out event; if no check-out occurs within the gym's configured max session duration, system shall auto-check-out and flag the record. |
| FR-ATT-003 | System shall block a new check-in for a member with an already-open (not checked-out) session. |
| FR-ATT-004 | System shall block check-in for a member whose membership is not `active` (expired/frozen/cancelled), with a clear reason shown to staff. |
| FR-ATT-005 | System shall compute daily/weekly/monthly attendance and attendance percentage per member. |
| FR-ATT-006 | System shall render an attendance calendar (per member, per month) marking present/absent/frozen days. |
| FR-ATT-007 | System shall compute current streak and longest streak per the gym's configured streak rules. |

## 6.7 Workout Management (WRK)

| ID | Requirement |
|---|---|
| FR-WRK-001 | Owner/Trainer shall create workout templates composed of exercises with target sets/reps/weight/rest, organized by day. |
| FR-WRK-002 | Trainer shall assign a workout template (as-is or customized) to an assigned member with a start date and schedule. |
| FR-WRK-003 | Member shall view today's assigned workout and mark each exercise/session as completed, skipped, or partially completed. |
| FR-WRK-004 | System shall retain full workout history per member, including per-exercise actuals, for trend and PR (personal record) computation. |
| FR-WRK-005 | System shall detect and flag a new PR when a logged set exceeds the member's prior best for that exercise (by weight or by reps at equal/greater weight). |

## 6.8 Diet Management (DIET)

| ID | Requirement |
|---|---|
| FR-DIET-001 | Trainer shall create diet plan templates with meals (name, time slot) and macro targets (calories, protein, carbs, fat). |
| FR-DIET-002 | Trainer shall assign a diet plan to an assigned member. |
| FR-DIET-003 | System shall track daily water intake logging (member self-entry). |
| FR-DIET-004 | Trainer shall record supplement recommendations and daily adherence notes per member. |

## 6.9 Progress Tracking & Body Measurements (PROG)

| ID | Requirement |
|---|---|
| FR-PROG-001 | Trainer (or member self-entry, if gym allows) shall record body measurements: weight, height, BMI (auto-calculated), body fat %, muscle %, chest, waist, shoulder, arms, legs. |
| FR-PROG-002 | System shall support progress photo upload with pose tag (front/side/back) and date. |
| FR-PROG-003 | System shall generate month-over-month comparison views and trend charts per metric. |
| FR-PROG-004 | System shall render a transformation timeline combining dated photos with concurrent metric values. |

## 6.10 Payment Management (PAY)

| ID | Requirement |
|---|---|
| FR-PAY-001 | Staff shall record a payment against a member for a membership renewal, upgrade, or ad-hoc charge, specifying method (Cash/UPI/Card/Bank Transfer). |
| FR-PAY-002 | System shall generate a PDF invoice and printable receipt for every recorded payment, with a gym-sequential, immutable invoice number. |
| FR-PAY-003 | System shall track pending dues per member and surface a gym-wide dues list. |
| FR-PAY-004 | Staff shall apply a discount (percentage or flat amount) to a transaction, with a required reason note. |
| FR-PAY-005 | System shall maintain a complete, append-only payment history per member (no hard delete of financial records; corrections are reversal entries). |

## 6.11 Expense Management (EXP)

| ID | Requirement |
|---|---|
| FR-EXP-001 | Owner shall record an expense with category, amount, date, vendor/note, and optional receipt attachment. |
| FR-EXP-002 | System shall generate a monthly expense report grouped by category. |
| FR-EXP-003 | System shall compute a Profit/Loss summary as (total revenue in period) − (total expenses in period). |

## 6.12 Reports (RPT)

| ID | Requirement |
|---|---|
| FR-RPT-001 | Every report listed in [12-report-design.md](12-report-design.md) shall support search, column filters, sorting, and export to CSV, Excel, and PDF, plus browser print. |
| FR-RPT-002 | Report exports shall respect the requesting user's role scope (e.g., a Trainer's export of "member reports" is limited to their assigned members). |
| FR-RPT-003 | System shall log every report export (who, what report, what filters, when) to the audit log. |

## 6.13 Notifications (NOTIF)

| ID | Requirement |
|---|---|
| FR-NOTIF-001 | System shall generate in-app notifications for: membership expiry, fee due, attendance reminder, workout reminder, diet reminder, birthday, and gym/platform announcements. |
| FR-NOTIF-002 | Each user shall have per-category notification preferences (in-app always on; email opt-in at v1.x). |
| FR-NOTIF-003 | System shall deduplicate notifications (e.g., do not send the same expiry alert twice for the same event/day). |

## 6.14 Messaging (MSG)

| ID | Requirement |
|---|---|
| FR-MSG-001 | System shall allow a 1:1 conversation thread between a Trainer and each of their currently-assigned Members. |
| FR-MSG-002 | System shall support text, image, and PDF message content types, with server-side file-type and size validation. |
| FR-MSG-003 | Reassigning a member to a new trainer shall preserve message history but start a new active thread context with the new trainer; the old trainer loses further send/receive access. |

## 6.15 Dashboard & Analytics (DASH)

| ID | Requirement |
|---|---|
| FR-DASH-001 | System shall render a role-specific dashboard on login, populated with live data scoped to that user (see [13-dashboard-design.md](13-dashboard-design.md)). |
| FR-DASH-002 | Owner dashboard shall reflect same-day data (today's check-ins, revenue) with no more than a 1-minute staleness (cache-and-invalidate, not real-time streaming, at v1). |

## 6.16 Settings (SET)

| ID | Requirement |
|---|---|
| FR-SET-001 | Owner shall configure gym-level settings: attendance rules, streak rules, notification templates, invoice numbering format, default currency/tax rate. |
| FR-SET-002 | Platform Super Admin shall configure the subscription plan catalog and per-plan feature entitlements, which gate module/feature availability per tenant in real time. |

## 6.17 Streak & Gamification (STRK)

| ID | Requirement |
|---|---|
| FR-STRK-001 | System shall award a streak day when the gym-configured combination of check-in / workout-logged / check-out is satisfied within one calendar day. |
| FR-STRK-002 | System shall allow a member a configurable number of "streak freezes" per period, consumed automatically to preserve a streak on a missed day if available. |
| FR-STRK-003 | System shall support member-declared vacation mode (staff-approvable) that excludes the date range from streak-break and attendance-percentage calculations. |
| FR-STRK-004 | System shall award badges at configured streak/attendance milestones and display them on the member's profile. |
| FR-STRK-005 | System shall compute an opt-in gym-scoped leaderboard ranked by current streak (ties broken by longest streak); members not opted in are excluded from display but still tracked internally. |
